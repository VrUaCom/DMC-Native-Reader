# План порту: одне ядро для Android, Windows, macOS та iOS

Дата: 2026-11-18, стан оновлено 2026-11-19. Гілка `NR-Luna-v73` (Android v151; macOS — рівень Android, крім GPU-рендеру).

## 1. Принцип

Одне ядро C++23 (`app/src/main/cpp`, близько 52 тис. рядків без оболонок) вирішує все:
- що за файл і як його відкрити;
- як його намалювати;
- текст Info і здоров'я файлу;
- меню, налаштування, стрічку анімацій, базову кімнату, камеру гри.

Оболонка кожної платформи лише:
- читає файли, які дав користувач;
- показує те, що намалювало ядро;
- зберігає вибір користувача;
- відтворює звук і відео, які ядро розкодувало;
- малює вікна, кнопки й жести у стилі платформи.

**Одна межа між ядром і оболонками — C API** (`capi/include/dmc_reader.h`). Зараз Android ходить через власний JNI, а Windows викликає C++ ядра напряму. Мета — щоб усі чотири платформи йшли через той самий C API. Тоді кожна функція, додана в ядро, автоматично доступна всім, а тест C API перевіряє межу для всіх одразу.

## 3. Чого не вистачає

### 3.1. Ядро: рішення, що ще живуть у Java

- **Відкриття складених сцен** (#42): додавання PAC до персонажа, складання кількох MOD, PTX на частину моделі. Java досі сама вирішує порядок і назви.
- **Стан перегляду** (#45):
  - камера (поворот, зум, зсув, політ, «рівень»);
  - стек навігації «Назад»;
  - панель варіантів (позиції ворога).

  Це 2,2 тис. рядків `DmcRenderView` разом із математикою жестів. Без цього кожна оболонка писатиме камеру заново.
- **Тайм-лайн відтворення:** кадр анімації, швидкість, цикл, синхронізація звуку катсцени. Зараз його веде Java.
- **Налаштування фото/відео камери:** схема вже в ядрі (`spider/camera.h`), але передається рядками з табами; потрібна така сама типізована схема, як у налаштувань перегляду.

### 3.2. Межа: C API проти JNI

Докладна таблиця всіх 147 функцій JNI, правила межі (рядки, списки, буфери, володіння, потоки) і баги, знайдені під час огляду, — у [`docs/port/C_API_MIGRATION.md`](port/C_API_MIGRATION.md). Група 1 уже в C API.

У C API 44 функції (23 з v1 і 21 з групи 1), у JNI 147. Решту додавати групами, кожну з тестом у `c_api_test`:
1. відкриття: `openResource`, діти, композиція MOD, PTX, додані PAC;
2. рендер: кадр, вибір під пальцем (pick), утримання, бенчмарк, експорт PNG і UV;
3. анімації: стрічка, завантаження MOT і MotionScript, кадри, класові події;
4. стейджі: кімната, ефекти, конфіг, точки появи, камера гри, Stage Ops, картки маркерів;
5. меню: компаньйон-меню, меню ефектів і звуку, дії;
6. катсцени: PCM, субтитри, камера, вібрація;
7. відео: кадри WMV;
8. фото камера: план, фокус, поляризатор, DNG;
9. діагностика: звіт падіння, лог, здоров'я, перекодування текстур.

Наприкінці JNI стає тонкою обгорткою над C API. Тоді Android перевіряє ту саму межу, що й решта платформ.

### 3.3. GPU на інших платформах

GPU-рендер написаний на OpenGL ES 3 (`android/gles_view_backend.cpp`, 1,8 тис. рядків) разом із 67 шейдерами DMC3. Специфічних для Android місць у ньому лише три: вікно `ANativeWindow`.

**Пропозиція: ANGLE.** Це бібліотека Google, яка виконує OpenGL ES поверх Metal (macOS, iOS) і Direct3D 11 (Windows); на ній працюють Chrome і Firefox. Так той самий рендер і ті самі шейдери запрацюють на трьох нових платформах після заміни лише прив'язки до вікна.
- Ризик: ANGLE великий і збирається складно. Готові збірки (наприклад, порт `angle` у vcpkg) треба перевірити першою збіркою.
- Запасний шлях: власний бекенд на Metal (Apple) і на Direct3D 11 (Windows). Шейдери в такому разі перекладаються механічно (GLSL → SPIR-V → MSL/HLSL через SPIRV-Cross). Це більше роботи, зате без залежності.

### 3.4. Відео

FFmpeg уже збирається мінімальною конфігурацією для Android (лише ASF + WMV/VC-1 + WMA). Ту саму конфігурацію треба ввімкнути для macOS, Windows та iOS. Системні декодери WMV не підтримують: AVFoundation на Apple не читає WMV, а Media Foundation на Windows читає, але це був би окремий шлях лише для Windows.

Для iOS треба перевірити ліцензію: FFmpeg — LGPL, а статичне лінкування в застосунок App Store має свої умови. Можливе рішення — FFmpeg як окремий dynamic framework.

### 3.5. Звук

Ядро вже розкодовує звук (VAG, OGG), а відтворює його кожна оболонка своїм кодом. **Пропозиція:** відтворення теж перенести в ядро через miniaudio. Це одна бібліотека з одного заголовка (public domain / MIT-0), яка працює на WASAPI (Windows), CoreAudio (macOS, iOS) і AAudio (Android). Тоді синхронізація звуку з катсценою буде в одному місці, а не в чотирьох.

### 3.6. Оболонки

- **Android:** готова. Далі тільки переведення JNI на C API.
- **Windows:**
  - перевести з прямих викликів C++ на C API;
  - прибрати конструкції, які збирає лише MSVC (відкриття файлу через `wstring`, `wmain`): тоді збиратимуть і MSVC, і MinGW;
  - додати збірку в CI;
  - підтягнути до рівня Android за пунктами з таблиці.

  **Рішення: Win32 лишається.** Залежностей немає, і 2,8 тис. рядків уже є. За master plan від вересня Windows має стати «робочим столом» дослідника, з кількома вікнами, тож перехід на інший інструментарій можна обдумати пізніше, якщо Win32 почне гальмувати роботу.
- **macOS:**
  - 0.1 є; її треба зібрати на твоєму M1 і виправити те, що не збереться;
  - далі за таблицею: GPU, налаштування, анімації, стейджі, катсцени.
- **iOS:**
  - нова оболонка, але більшість коду SwiftUI спільна з macOS: `ReaderCore.swift` і `ViewerModel` майже без змін;
  - своє тут: відкриття файлів з «Файлів» (document picker), жести дотику замість миші, ARKit пізніше.

### 3.7. Збірка, CI, перевірка

- **CMake presets** для чотирьох цілей: `android-arm64`, `windows-x64` (MSVC), `macos-arm64`/`macos-x86_64`, `ios-arm64` + симулятор.
- **GitHub Actions** (Android уже є):
  - Windows: збірка і запуск `c_api_test` на `windows-latest`;
  - Apple: на `macos-14` (M1) збірка ядра, `c_api_test`, Mac-застосунку і iOS-симулятора;
  - Linux: хостові тести, libc++ і MinGW.
- **Перевірка перед кожною збіркою, що йде людям:**
  - Android: `tools/emulator_smoke.sh`;
  - desktop: той самий набір файлів через C API без вікна (відкрити, намалювати, Info, здоров'я);
  - iOS: симулятор.
- **Роздача:** усе йде релізами на GitHub, як Android. Apple нічого не платимо, сертифікатів не купуємо. Хто хоче, той ставить.
  - Android: APK, тестовий ключ, як зараз;
  - macOS: `.app` у zip. Підпис ad-hoc (`codesign -s -`) безкоштовний і робиться збіркою сам; без нього M1/M2 взагалі не запустить програму. На чужому Mac перший запуск: правий клік → «Відкрити» (або `xattr -dr com.apple.quarantine`);
  - iOS: непідписаний `.ipa` з CI (`xcodebuild` без підпису). Людина ставить його собі сама: Sideloadly, AltStore або SideStore зі своїм Apple ID, або TrollStore там, де він працює. Це її справа, не наша;
  - Windows: `.exe` у zip без підпису (SmartScreen: «Докладніше» → «Однаково запустити»).

## 4. Сховище Obsidian: що там є і як його використати

Робоче сховище — спільна тека Drive `DMC Rengine` → `DMC3-Reverse-Gemma` (`.obsidian` поруч, оновлюється щодня).

**Що в ньому:**
- Статичний реверс того самого `dmc3.exe` (SHA `e454272e…dcbdd082`, тієї самої версії, з якою працюють Reader і rengine).
- 9 673 з 10 152 функцій мають нотатку (95,3%) у 31 підсистемі: render 311, effects 246, ui 386, motion 165, stage 110, camera 81, sound 36, media 17 та інші.
- Класи RTTI з деревом успадкування і слотами vtable (CPlDante, CPlVergil, CPlLady, CEm010…).
- `Structs/`, `Formats/` (MOD/SCM, MOT, PAC/PNST, PTX/DDS, Effects, EventTbl, Stage rooms, Collision).
- Розділ `Native Reader/` з нотатками про нашу гілку.

**Головне застереження.** Лише 50 нотаток перевірено інструментами (REA), а позначки `verified` ще не має жодна. 6 081 нотатка — гіпотези моделей (Gemma, Codex), і в багатьох низька впевненість. Тому сховище — це карта: де шукати і що перевірити. Фактом воно не є.

**Як воно потрапляє в ядро** (те саме правило clean room, що й у самому сховищі та в нас):
1. Нотатка сховища дає адресу і гіпотезу.
2. Гіпотеза перевіряється на EXE (`dmc3-gates` у dmc-rengine-cpp) і на справжніх файлах гри.
3. Перевірене записується як специфікація в `docs/cleanroom/specs-*` (лише поведінка і дані, без коду гри).
4. Код у ядрі пише окремий агент тільки зі специфікації.

**Де сховище допоможе найбільше:**

| Що в Reader | Підсистема сховища | Що дати ядру |
|---|---|---|
| Світло і туман стейджу (зараз «експериментально») | render (311) | вибір джерел світла для кожного об'єкта, одиниці кольору, туман |
| Камера гри між зонами (у нас «не встановлено») | camera (81) | змішування камер при переході між зонами, рейки |
| Ефекти (генератори, частинки) | effects (246), Structs Effect instance | час життя, батьківські прив'язки, генератори G |
| Звук стейджів і персонажів | sound (36: декодер VAG reviewed, банки) | вибір семплу з банку за ключем, канали |
| Відео катсцен | media (17) | ціль 1280×720, стани відтворення |
| Ламані об'єкти стейджу | stage (110) | `SET n BREAK`, перемикання на ламану модель |
| Анімації, MotionScript | так | ні | так | — |
| Персонажі | Classes CPl*, CEm* | збирання костюмів і зброї, Lady як гравець |

Пропоную також у зворотному напрямку: після кожного релізу Reader оновлювати `Native Reader/Findings.md` у сховищі тим, що Reader підтвердив на файлах. Тоді гіпотези сховища отримують перевірку з нашого боку.

## 6. Рішення, потрібні від тебе

1. **GPU:** ANGLE (один рендер для всіх, швидше) чи власні Metal і Direct3D (більше роботи, без великої залежності)? Пропоную ANGLE.
2. **Звук у ядрі через miniaudio** замість окремого коду в кожній оболонці? Пропоную так.
3. ~~Windows: лишити Win32?~~ **Вирішено: лишаємо.**
4. ~~Платити Apple?~~ **Вирішено: ні.** Релізи без платних підписів; хто хоче, той ставить (див. «Роздача» в 3.7).
5. **Доступ до Mac:** тека з репозиторієм у Claude → Settings → Claude Code → Remote Control, щоб я сам збирав і перевіряв macOS та iOS.
6. **Сховище:** чи можна після релізів дописувати в `Native Reader/Findings.md` те, що Reader підтвердив на файлах? Правила сховища вимагають для цього резервну копію і рядок у журналі змін.
